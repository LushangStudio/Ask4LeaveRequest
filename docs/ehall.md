# ehall 接入与验收边界

参考用户提供的《ehall 请假审批与请假条自动生成 PRD》，并采用 2026-09-23 的补充要求：事项可为课程、活动或其他类型；多个事项默认合并出条，也允许分别生成；所有信息先入库；暂不做验真、签名。

## 已实现

自适应网页、固定演示角色、服务端分配审批人、统一整份审批、结构化事项、数据库留存、审批快照、中文 PDF、文件失败重试、历史查询和访问隔离。

## 需要平台提供

- 登录协议、受众校验规则和可验证的身份来源；不能信任浏览器提交的身份或角色。
- 学生与辅导员的权威映射和更新机制、无人接收的处理方式。
- 审批流由平台承载还是自建服务承载，以及待办/消息接口。
- 正式请假条模板、附件规则、数据访问与保留要求。

## 替换方式

保留申请/事项/审批/文件模型。用可验证的平台登录适配器替换 `/api/demo/login` 和演示种子数据，由权威身份映射到 people。若采用平台审批，服务端回调必须验签、防重放，验证审批者及范围后调用同一审批事务。禁止仅凭请求中的姓名或学号认定身份。

尚未实现上述适配器，APP_MODE=production 会直接拒绝启动。生产身份隔离、CSRF 防护、HTTPS Cookie、速率限制、日志脱敏、异步生成租约、数据库迁移与恢复演练完成后才能开放公网路由。演示中不接收真实证明材料；附件功能仍待业务规则确认。

## 验收场景

手机提交课程与活动混合事项 → 辅导员通过 → 学生下载合并 PDF；再用分别生成模式验证文件数量。驳回必须填写原因且不能下载文件；两组学生/辅导员相互不可见。模拟字体不可用后应出现“审批已通过，文件生成失败”，恢复字体后可重试，无需再次审批。记录重启后仍可查询。
