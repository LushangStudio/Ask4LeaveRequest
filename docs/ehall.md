# ehall 接入与验收边界

参考用户提供的《ehall 请假审批与请假条自动生成 PRD》，并采用补充要求：事项可为课程、活动或其他类型；多个事项默认合并出条，也允许分别生成；所有信息先入库。2026-10-12 增加班级与多辅导员运维关系配置、签名截图裁切、带纯黑点阵水印签名及审批前预览；尚不做密码学验真。

## 已实现

自适应网页、运维配置的班级和演示角色、班级任一辅导员单次审批、统一整份审批、结构化事项、数据库留存、审批和带水印签名快照、审批预览、中文 PDF、文件失败重试、历史查询和访问隔离。

## 需要平台提供

- 登录协议、受众校验规则和可验证的身份来源；不能信任浏览器提交的身份或角色。
- 已采用运维管理的班级 JSON 作为审批关系来源；学校需确认学工号口径与名单维护流程，正式身份只匹配名单，不让学生自行指定班级或审批人。
- 审批流由平台承载还是自建服务承载，以及待办/消息接口。
- 正式请假条模板、附件规则、数据访问与保留要求。

## 替换方式

保留申请/事项/审批/文件/签名快照模型。用可验证的平台登录适配器替换 `/api/demo/login` 与公开演示身份枚举，由已验证学工号精确匹配运维名单。若采用平台审批，服务端回调必须验签、防重放，验证审批者及范围，并补齐预览与签名授权后调用同一审批事务。禁止仅凭请求中的姓名或学号认定身份。

已实现 WordTxT 同款 UIS 授权码流程、一次性 state、严格用户信息与空学工号校验、独立生产会话与全局 GLO 退出，且没有本专科生类型限制。生产必须具备 UIS 凭据、HTTPS 回调与运维名单，缺配置仍拒绝启动。正式 UIS 注册回调和实账号登录需部署时验收；ehall 平台审批/待办接口、异步任务租约与附件规则仍属于后续边界。演示登录不能开放到公网；受控 test- 密钥入口与 UIS 独立。

## 验收场景

手机提交课程与活动混合事项 → 辅导员通过 → 学生下载合并 PDF；再用分别生成模式验证文件数量。驳回必须填写原因且不能下载文件；两组学生/辅导员相互不可见。模拟字体不可用后应出现“审批已通过，文件生成失败”，恢复字体后可重试，无需再次审批。记录重启后仍可查询。
