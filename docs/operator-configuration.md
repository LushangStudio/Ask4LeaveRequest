# 当前配置方式

班级关系已改为数据库持久化，通过独立管理员页面管理，并支持 CSV 批量导入。生产不再读取关系 JSON。管理员配置、一次性旧名单迁移和上线步骤见 [class-management.md](class-management.md)。下方 JSON 内容仅用于旧文件迁移和本地虚构 fixture 参考。

# 班级关系与辅导员签名

师生关系由运维 JSON 或配置中的管理员维护。普通学生和辅导员没有导入、分班或调整审批人的入口。在线管理与部署升级见 class-management.md。

## JSON 格式

结构参考 `config/relationships.example.json`。该文件只含虚构演示身份，展示两个班级、三位辅导员；辅导员丙同时负责两个班级。

```json
{
  "version": 1,
  "counselors": [
    { "user_id": "STAFF001", "name": "示例老师甲" },
    { "user_id": "STAFF002", "name": "示例老师乙" }
  ],
  "classes": [
    {
      "class_id": "class-2026-a",
      "name": "2026 级示例一班",
      "counselor_ids": ["STAFF001", "STAFF002"]
    },
    {
      "class_id": "class-2026-b",
      "name": "2026 级示例二班",
      "counselor_ids": ["STAFF001"]
    }
  ],
  "students": [
    {
      "user_id": "STUDENT001",
      "name": "示例同学",
      "class_id": "class-2026-a",
      "college": "示例学院",
      "major": "示例专业",
      "grade": "2026"
    }
  ]
}
```

`user_id` 对应身份上游返回的学工号，必须用字符串，以保留前导零；当前演示文件使用虚构标识。学生学号直接取 `user_id`。一个学生只出现一次，只能填写一个 `class_id`。班级至少有一位辅导员；辅导员可出现在多个班级。班级 ID 与学工号仅接受字母、数字、下划线、连字符，首尾空白会去掉。未知字段、空值、重复学工号/班级、重复 JSON 字段、未知班级/辅导员和兼任两种角色却使用不同姓名均拒绝。

## 运维更新流程

1. 在服务器受控目录准备新文件，例如 `/etc/ask4leave/relationships.next.json`，不要上传到前端资源目录或提交 Git。
2. 用同一 release 的虚拟环境校验：`/opt/ask4leave/current/.venv/bin/python -m app.directory /etc/ask4leave/relationships.next.json`。需在 release 工作目录执行。成功只输出人数，不打印个人资料。
3. 备份原配置与数据库；确认变更名单，设置配置所属 `root:ask4leave`、权限 `0640`，原子替换 `relationships.json`。
4. 环境设置 `RELATIONSHIPS_PATH=/etc/ask4leave/relationships.json` 后重启服务。校验失败会拒绝启动，不回退到演示名单。检查健康和两组权限。
5. 新配置在单次事务中同步到数据库。取消配置的身份立即失去旧会话访问权限，但历史人员和申请、审批、文件不会删除。可新增或移除兼任身份，既有单一角色不直接互换。

重启才会读取更新，不热加载文件。新申请保存提交时的班级与全部辅导员范围快照；在这些辅导员中任意一位完成审批即可。班级变更仅影响后续申请，既有申请不会自动改派。若要改派未处理申请，需要另行设计带审计的管理操作。已通过/已驳回申请不可再审批；同一实际审批人的网络重试仍幂等，其他辅导员即使提交相同意见也返回冲突。

本地默认读取示例文件。自定义演示名单同样由运维放到本地受控文件并指定 `RELATIONSHIPS_PATH`，浏览器只提供身份切换用于本地测试。

## 签名与预览

辅导员本人上传 PNG、JPEG 或 WebP 静态截图，在前端自由选区、移动和拖动四角裁切，也可输入像素坐标。前端仅发送裁切结果。服务器重新解码、限制文件大小（3 MiB）和总像素数（1200 万），转存 PNG、剥离元数据，不信任文件扩展名。只有本人可访问自己的未加水印签名。

审批通过前必须保存签名并生成预览。合并模式预览一份，分别模式预览每一事项的一份 PDF；前端要求逐份切换核对。预览保留 15 分钟，绑定申请、实际审批人、签名版本及审批意见；意见变动、签名变更或过期都须重新预览。驳回不要求签名。

签名中的水印为 `姓名-起始日期-天数`，例如 `示例同学-2026-10-10-3天`。天数含起止当天，与分别/合并生成方式无关。密集黑点文字叠在稀疏黑点底纹上，重复覆盖签名区域；所有水印像素均为不透明纯黑，没有灰色或半透明像素。水印烧入 PNG，PDF 只嵌入带水印图片，不另藏原始签名。简单全局二值化不能只删水印、保留同样黑色的笔迹；图片处理仍可能去除或重绘，当前功能不等同密码学电子签名。

通过审批时将本次带水印图片和摘要与审批记录一并保存。个人签名更换、文件生成失败后重试都使用历史快照。旧系统已有审批没有签名，不会补用当前签名伪造历史签署；已有 PDF 保留原内容，旧审批重新生成时标注“历史审批未留存签名”。

## 存储变更

增加 `directory_members`、`request_counselors`、`counselor_signatures`、`approval_signatures`、`approval_previews` 五张表，不修改旧表列。现有 `counselor_id` 列仅为兼容旧结构，新权限以 `request_counselors` 为准。启动为旧申请补一条原辅导员范围记录，不给旧审批补签名。

新空库参考 `docs/schema.mysql.sql`；既有 MySQL 库使用 `docs/migrations/002-class-signatures.mysql.sql`，由迁移账号执行。运行账号不应有建表权限。本地 SQLite 在启动创建新增表并补范围记录。迁移前先备份，迁移和应用版本必须一起验收；签名、预览与 PDF 都属于受控数据库数据。过期预览在启动及创建新预览时清理。

生产已接入与 WordTxT 相同的 UIS 协议，不按本专科生类型限制；尚未登记在运维名单的学工号不能获得应用角色。可设置 `TEST_RELATIONSHIPS_PATH` 合并独立 test- 名单，重复身份和班级仍拒绝。空正式名单可用于首次部署，仅附加测试名单时只能通过测试入口使用虚构账号。真实 UIS 凭据与回调授权由部署时验证。

## 同时作为学生与辅导员

同一个 user_id 可以在 students 和 counselors 中各出现一次，姓名必须一致。学生仍只有一个 class_id；该用户可作为若干班级的 counselor_ids，包括自己所在班级，允许为自己审批。数据库以 both 保存兼任身份，界面提供学生/辅导员视角切换，分别只列本人申请与负责的班级申请。后端仍检查提交者身份、申请所属班级和辅导员授权，不根据界面选择授予权限。无需修改表结构。
